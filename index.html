Who this is from

I'm Rick. I've spent 25+ years running commercial and industrial construction jobs — owner's rep side. Now I'm building software with AI agents, and I run them the way I'd run a jobsite: clear scope, hard rules, independent inspection, and I don't stand over anyone's shoulder.

01 — The map

How a piece of work moves

Work enters as a GitHub issue. A timer fires every 30 minutes. Each tick, the factory does only what the autonomy dial allows — implement, validate, merge, deploy — and everything it does leaves a label on the issue, so the whole audit trail is readable from my phone.

The dial

0 = everything by hand. 1 = it may open PRs. 2 = it may validate them. 3 = it may merge green work and deploy. I turned it up one notch at a time, and before every notch the gate had to prove it could still fail. A gate that can't fail isn't a gate.

The stop button

Two of them, on purpose. touch .factory/STOP works with the network down. Labeling any open issue factory:stop works from my phone in line at the store. If the stop state can't be read, nothing runs. Fail closed or don't bother.

The rules it can't touch

Three files govern everything: what the product is, how the factory must behave, and how the code is written. No agent may edit the rules it's judged by. Changes to those files are human commits only — and that's enforced in code, not vibes.

03 — When it broke

Yes, it misfired. Here's what that looked like.

Anyone showing you an autonomous system that "just works" is editing the tape. Here's my favorite failure.

Two PRs finished at nearly the same time and both wanted the same migration number — like two subs both claiming the same parking spot. I'd built a fix: on rebase, the factory renumbers the loser automatically. Tested it interactively. Worked great.

First live run under the scheduler? The scheduler's environment doesn't have node on its PATH. The check couldn't run its own tooling — and it read its own failure as "duplicate migration found," then escalated to me with a completely fabricated story about a collision that didn't exist.

  • The fix wasn't clever: resolve the tool absolutely, skip the check when a branch has no migrations at all, and — the real lesson — never let "my tooling broke" and "I found a problem" share an error code.
  • The regression test now extracts the live functions out of the running script, verbatim, so the test literally cannot drift from the code it's testing.
  • The whole saga — bug, fix, and self-test — ships in the public repo below. Nothing sanded off.

The doctrine that came out of it

A silent skip is a failure. Every conditional check must print a conclusion — ran and passed, ran and failed, or skipped and said why. "Empty is not pass" is written into the gate's contract, because an unattended system that skips quietly looks exactly like one that checked.

04 — The one tip

The system runs in parallel with my life

If I could hand you one thing from all this, it's not a prompt or a model setting. It's this: stop sitting there watching your agents. The time saved isn't minutes per task — it's that I'm never at the keyboard waiting.

Three pieces make that real:

  • Escalation finds me; I don't poll it. The only state that reaches my phone is "needs a human." Everything else is the machine talking to itself. Notifications go local feed → email → Slack, in that order, and the notify script is written so an escalation can never be the thing that fails — a dead webhook degrades to the log, never to an error.
  • The queue and the controls are phone-shaped. Work enters as a GitHub issue (I file them from the truck). The audit trail is labels. The stop button is a label. I can start, read, and stop the whole thing without a laptop.
  • Check-ins are remote-control sessions. When something does need me, I open Claude Code remote control from my phone, look at what the factory parked, nudge it, and get back to my day.

The honest version of the tip: you can't walk away from agents you don't trust, and you shouldn't trust agents you haven't fenced. The dial, the gates, the stop buttons — all that boring safety rail is what buys the walking away. Same as a jobsite: nobody "supervises harder" their way to safety. You build the system so the default is safe, then you go live your life.

05 — The brain

My agents never relearn anything

The factory is half the story. The other half: every session, every agent, wakes up already knowing who it works for, what's been decided, and what's currently true — because memory lives in a small git repo, not in anyone's context window.

The loading trick is a ladder, and it's the only load-bearing part:

  • Always: one small identity file (who I am, what I know cold, what's locked) and one global memory file (decisions + open questions).
  • Only when a project comes up: that project's state file. The active project gets depth; side projects get one page.
  • Only when named: the deep archive — decision records, prompt history, lessons. Never pre-loaded.

Two files always, everything else earns its way in. Decisions live in two sections — locked and open — and deciding something means moving the line between them, with a date and a name. Every session ends with three lines in a daily log: worked on, decided, open. Thirty seconds of discipline, and the next session starts warm.

My real brain repo stays private — it's full of my business. But the pattern is public as a fill-in-the-blanks starter, loader skill included.

Honest expectations

  • It is not a framework. It's a working machine, extracted honestly — some parts are shaped like the project it came from, and a file named ADAPTERS.md tells you exactly which ones.
  • It will not run unattended on day one. It starts at dial 0 with a human signing every piece of work, and it should. You earn each notch.
  • What you get on day one: the gates, the judges, the protected-file guard, the stop buttons, and a binding procedure that refuses to finish until the gate proves it can fail.
